Two real bugs found and fixed during the browser walkthrough:

- **`OptionSetPicker` renders its own inline `<form>`** (via `OptionSetForm`) when creating/editing an option set. Any modal that wraps `OptionSetPicker` in its own outer `<form>` (as `BoardCreateModal` originally did) creates a nested-`<form>` DOM structure, which is invalid HTML — submitting the inner form bubbles a native `submit` event up to the outer form too, and since HTML can't nest forms, the browser falls back to a real (unintended) page navigation/reload, silently wiping all component state. Fixed by making `BoardCreateModal`'s wrapper a plain `<div>` with an explicit `onClick`-triggered submit instead of a `<form onSubmit>` (see `src/app/boards/BoardCreateModal.tsx`). Also noted: `OptionSetPicker`'s inline "create new" flow leaves its own dropdown open afterward (pre-existing behavior shared by every consumer, e.g. `AddPropertyControl`) — not a bug, just something a caller's own UI/tests need to account for (click the trigger again, or click away, to dismiss it).
- **Duplicate React `key` across sibling elements of different component types.** `NotePage.tsx`/`BoardPage.tsx` originally keyed both the existing content component (`NoteBlockList`/`KanbanBoard`, `key={note.blockDocId}` / `key={board.cardsDocId}`) _and_ the new `StickyNotesSection` sibling with the exact same docId string as the key. React's keyed-children reconciliation doesn't care about component type — two siblings under the same parent with an identical `key` is invalid regardless of whether they're the same component, and reliably reproduced (even on a page with zero sticky notes ever touched) as a console "Encountered two children with the same key" warning plus genuinely flaky behavior downstream (observed: a just-typed sticky note's debounced text failed to persist in one run, traced back to this, not a real save-path bug — see the isolated repro that ruled it out). Fixed by giving `StickyNotesSection` a namespaced key (`` `stickies-${docId}` ``) in all three pages instead of reusing the bare docId. **Rule of thumb**: never reuse an entity's raw id/docId as a `key` on more than one sibling element, even across unrelated components.

**Not separately verified via Playwright**: sidebar drag-and-drop reparenting (for folders _or_ the newly-added notebooks/boards) — confirmed this is a pre-existing simulation limitation, not a regression: the exact same scripted pointer-drag sequence also fails to reproduce a move on unmodified `main` for plain folder-to-folder dragging. The "Move to..." modal path (which shares the same `moveFolder`/`moveNotebook`/`moveBoard` calls) is fully Playwright-verified instead; the drag wiring for notebooks/boards mechanically mirrors the already-shipped, working `FolderTreeNode` folder-drag pattern (prefixed id + grip handle + `useDraggable`, no `useDroppable` since they can't contain children).

## 5. Sticky Notes — absolutely-positioned overlay + mobile gallery

**Key decision, confirmed with the user**: sticky notes do **not** live in a bounded canvas panel. They're `position: absolute` elements floating directly over existing page content (Note/Board/Notebook), anchored to the page's document flow so they scroll with nearby content, shown/hidden via a per-entity toggle. This is simpler than the original sketch below (kept struck through for context) and means **`@dnd-kit/modifiers` is not needed** — dragging is unconstrained (`useDraggable` + raw `event.delta`), no `restrictToParentElement`. In practice notes stay visually within `AppShell.module.css`'s `.main` scroll region anyway, since its `overflow-y: auto` makes `overflow-x` compute to `auto` too (CSS overflow-pairing) — they don't render over the sidebar/header chrome, which wouldn't be meaningful anyway since position is page-relative, not viewport-relative.

- **Types** (`src/domain/entities.types.ts`): `StickyColor = string` (hex from `PILL_PALETTE`) and `StickyNote { id, x, y, color, content: {kind:'text',text} | {kind:'sketch',strokes:Stroke[]} }` — **no `ownerId`** (deviates from the literal `spec.md` shape by decision): each owning Y.Doc only ever holds one owner's stickies, so it'd be dead weight, same reasoning as blocks not carrying a redundant `noteId`. Reuses the existing `Stroke` type (`src/domain/blocks/blocks.types.ts`).
- **Persistence**: `src/domain/stickyNotes/stickyNotesStore.ts`, mirroring `src/domain/blocks/noteBlocksStore.ts` exactly — `doc.getArray<Y.Map>('stickyNotes')` (distinct top-level array name so it coexists with `'blocks'`/card-order in the same `blockDocId`/`cardsDocId`), same `mutateAndPersist` helper. Functions: `loadStickyNotes`, `insertStickyNote`, `updateStickyNote`, `deleteStickyNote`, `moveStickyNote(docId, doc, id, x, y)`, `bringToFront(docId, doc, id)` (delete+re-append at array end, same technique `moveBlock` uses — array order = paint order = z-stack). React binding `src/app/stickyNotes/useStickyNotes.ts` mirrors `useNoteBlocks.ts` (`observeDeep` resync, caller remounts on doc change via a namespaced key, e.g. ``key={`stickies-${docId}`}`` — **not** the bare `docId`, since a sibling element on the same page is already keyed by that exact string; see the duplicate-key bug note above).
- **Color**: `pickLeastUsedColor(PILL_PALETTE, usedColors)` (`src/lib/color/leastUsedColor.ts`, already generic) at creation, scoped to the current doc's existing stickies only (own local pool, like board columns — not global like tags).
- **Drag mechanics**: plain `useDraggable` (`@dnd-kit/core`, already installed), no new dependency. `onDragEnd`'s `event.delta` added directly to stored `{x,y}`. Bring-to-front on drag start (pointer down), before the delta applies. Overlay wrapper is `pointer-events: none`; individual notes are `pointer-events: auto` — kanban DnD / block editing underneath stay fully usable while stickies are visible.
- **Creation**: a "+" button (not click-on-canvas — the overlay doesn't capture clicks except on existing notes), placed at a small cascading offset from the last-created note in that doc, content kind (text/sketch) chosen at creation and fixed after (not convertible).
- **UI** (`src/app/stickyNotes/`, new directory): `StickyNoteLayer.tsx` (overlay, conditionally mounted per the visibility toggle — same convention as `PropertiesPanel`/`BoardCardDetails`), `StickyNoteItem.tsx` (draggable + delete-x + renders text/sketch sub-editor), `StickyNoteTextEditor.tsx` (debounced textarea, reuses `SAVE_DEBOUNCE_MS`), `StickyNoteSketchCanvas.tsx` (new lightweight fixed-size pointer-capture loop, reuses `strokeToPath.ts` directly rather than reusing `SketchBlock.tsx` wholesale — that component is coupled to `NoteBlock`'s width/height/displayWidth/align), `StickyNoteGallery.tsx` (mobile-only via `useIsMobile()`, reuses `Modal.tsx`, grid of cards with position ignored, tap-to-expand inline rather than a nested modal), `useStickyNotesVisibility.ts` (per-entity toggle state, plain `localStorage` id set mirroring `useExpandedFolders.ts`, not `createLocalStorageKey`).
- **Wiring**: `EntityPageHeader.tsx` gains an optional `stickyNotes: {visible, onToggleVisibility, onAdd}` prop (same conditional-button convention as `wideMode`/`onToggleProperties`). `NotePage.tsx`/`BoardPage.tsx`/`NotebookPage.tsx` each add `position: relative` to their `.page` wrapper and mount `StickyNoteLayer` (desktop) or `StickyNoteGallery` (mobile) using `note.blockDocId`/`board.cardsDocId`/`notebook.stickyNotesDocId` respectively.
